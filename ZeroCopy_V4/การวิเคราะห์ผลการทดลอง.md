# การวิเคราะห์ผลการทดลอง Multi-threaded File Download

เปรียบเทียบ Traditional I/O กับ NIO Native Transfer (ไฟล์ 1000 MB, Windows 11, Java 23.0.1)

## การวิเคราะห์ผลการทดลอง

### สรุปผลที่วัดได้ (ค่าเฉลี่ย 3 รอบ)

| วิธี | 1 worker | 10 workers | Speedup |
| --- | --- | --- | --- |
| Traditional | 3.53 s (283.6 MB/s) | 8.12 s (123.2 MB/s) | 0.43 เท่า (ช้าลง) |
| NIO | 3.18 s (314.5 MB/s) | 2.96 s (337.8 MB/s) | 1.07 เท่า |

ทุกรอบผ่านการตรวจ size และ SHA-256 จึงยืนยันได้ว่าข้อมูลถูกต้อง ความแตกต่างอยู่ที่ประสิทธิภาพเท่านั้น

### ทำไม 10 workers จึงไม่เร็วขึ้น 10 เท่า

1. **ทรัพยากรที่ใช้ร่วมกันไม่ได้แบ่งตามจำนวน worker** การเพิ่มจำนวน thread ช่วยได้เฉพาะงานที่ขนานกันได้จริง แต่ที่นี่ทุก worker ใช้ CPU, memory bandwidth, loopback และดิสก์ชุดเดียวกัน เมื่อคอขวดอยู่ที่ทรัพยากรร่วม การเพิ่ม worker จึงไม่เพิ่มความเร็ว 
2. **Client และ Server อยู่บนเครื่องเดียวกัน** ทั้งสองฝั่งแย่ง CPU กันเอง ขณะที่ 10 workers ฝั่ง Client เปิดคู่กับ handler ฝั่ง Server ได้สูงสุด 20 thread รวมแล้วเกิด context switch และการแย่ง core มากขึ้น
3. **การเขียนไฟล์ปลายทาง 10 ตำแหน่งพร้อมกัน** แต่ละ worker เขียนคนละ offset ในไฟล์เดียวกัน ทำให้ดิสก์ต้องเขียนกระจายหลายตำแหน่ง และ OS ต้องจัดการ dirty page ของไฟล์ 1000 MB จึงอาจหน่วงงานเขียนได้
4. **ทรัพยากรของการทำงานหลาย thread** มีการสร้าง connection 10 ครั้ง, handshake, การจัดตาราง thread และ buffer ของแต่ละ worker ซึ่งเป็นต้นทุนเพิ่ม และมากกว่าที่ได้จากการขนานเมื่อทรัพยากรหลักอิ่มตัวอยู่แล้ว



### ทำไม NIO จึงไม่ชนะทุกครั้ง

- **ผลที่ได้:** ถ้าใช้ที่ 1 worker, Traditional เร็วกว่าชัดเจนในสองรอบแรก (ราว 800 MB/s เทียบกับ NIO ราว 370–395 MB/s) ส่วนที่ 10 workers NIO ชนะทั้งค่าเฉลี่ยและทุกรอบ
- **ข้อได้เปรียบของ NIO มีจำกัดบน localhost:** `transferTo/transferFrom` ลดการคัดลอกข้อมูลผ่าน user space ได้เมื่อ OS รองรับ แต่บน loopback ข้อมูลไม่ได้ผ่านการ์ดเครือข่ายจริง และ Traditional ที่ใช้ buffer  ก็มีประสิทธิภาพสูงอยู่แล้ว ส่วนต่างจึงเล็กลง


- **สาเหตุของรอบที่ช้าผิดปกติ:** อาจมาจาก Page Cache ถูกนออก, การ flush ข้อมูลลงดิสก์ในพื้นหลัง

**ข้อสรุป:** ไม่มีวิธีใดชนะในทุกเงื่อนไข ผลขึ้นกับจำนวน worker, สภาพของ cache และภาระของเครื่องขณะทดสอบ

## ******** ข้อจำกัดของการทดสอบผ่าน localhost

1. **Page Cache** หลังโหลดไฟล์ครั้งแรก  OS จะเก็บไฟล์ต้นทางไว้ใน RAM ทำให้ Server อ่านจากหน่วยความจำเป็นหลักแทนดิสก์ ตัวเลขจึงสะท้อนความเร็วของหน่วยความจำและ CPU มากกว่าความเร็วดิสก์จริง และอาจสูงกว่าสภาพใช้งานจริง ในทางกลับกัน ถ้า cache ถูกนำออกระหว่างรอบ เวลาน่าจะมีการเปลี่ยนแปลง
2. **Loopback network** การส่งผ่าน `localhost` ไม่ผ่านการ์ดเครือข่ายและไม่มีความหน่วงหรือแบนด์วิดท์จำกัดแบบเครือข่ายจริง ข้อมูลเป็นเพียงการคัดลอกในหน่วยความจำของ kernel ผลของการเพิ่ม worker  จึงไม่เหมือนสภาพจริง
3. **Storage cache** ดิสก์/SSD และตัวควบคุมมี write cache ของตัวเอง ประกอบกับ OS ใช้ write-back ทำให้เวลาเขียนไฟล์ปลายทางที่วัดได้อาจยังไม่รวมเวลาที่ข้อมูลถูกเขียนลงสื่อจริง และอาจไปกระทบรอบถัดไป
4. **Client และ Server ใช้ CPU และหน่วยความจำร่วมกัน** แต่ในสภาพจริงสองฝั่งอยู่คนละเครื่อง จึงไม่แย่ง CPU กัน ทำให้ผลที่ได้อาจต่างออกไป
